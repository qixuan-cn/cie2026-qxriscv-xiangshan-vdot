# 01 · 可行性分析

> 版本：V1 规格期 · 状态：草案（待评审）
> 本文所有新设计数字均为**目标值或预算值**；唯一标注"实测"的是既有 `vdot` FU 的综合与验证结果。

---

## 1. 需求与定位

### 1.1 要解决的问题

现有 `vdot` 指令族已经证明：在香山 VFEX0 上，一条 RISC-V 向量指令可以完成 8 路（INT8）或 16 路（INT4 / 三值）点积，1 inst/cycle、latency 3、无状态。但它只解决**寄存器级**的点积，不解决**tile 级**的矩阵：权重如何驻留、多行输出如何并行、K 维如何流式、结果如何只做一次浮点缩放。

RiscvTpu 要补的正是这一层。

### 1.2 目标（V1 必须达成）

| # | 目标 | 可验收形式 |
|---|---|---|
| G1 | 单卡可跑 `int8 / int4 / 三值` 三种精度的 GEMM 与 GEMV | 三个精度各有一个 tile 微基准，数值与软件黄金模型逐位一致 |
| G2 | 控制面是 RISC-V，不是私有宏指令 | 主机程序是 RV64 + RVV 代码；硬件只增加 CSR 与 64 B 描述符，不新增指令编码空间（`vdot` 系列除外） |
| G3 | 所有 tile 级结果都可用一组 `vdot` 指令逐位复算 | 存在等价的 RVV 软件实现，且位精确 |
| G4 | 面积/时序在 xc7k480t 单卡可容纳 | Yosys/Vivado 综合报告：LUT ≤ 预算 60k，fmax ≥ 100 MHz |
| G5 | 观测性是一等公民 | CSR 可读周期数、退休指令数、MAC 数、各精度退休数、访存停顿数 |

### 1.3 非目标（V1 明确不做）

- 多卡 / 多 slice 全收集（`GATHER`）——V2。
- 训练、反向传播、fp16/bf16 数据通路。
- 自研编译器与自研图 IR；V1 只做"描述符生成器 + 手写 tile 库"。
- 把 `vdot` 改成 openTPU 那样的 8×32-bit 宏指令（见 §5）。

## 2. 技术可行性

### 2.1 ISA 可行性：三条指令已经落地，不需要新的编码空间

| 指令 | 编码 | 语义 | 实测状态 |
|---|---|---|---|
| `vdot.vv` | `opcode=0x57, funct3=000, vm=1, funct6=111111` | 8×int8 点积，20 bit 输出 | 已实现、已综合、已协同仿真 |
| `vdot4x2.vv` | 同上，`funct6=111110` | 16 nibble 双结果 | 已实现 |
| `vtdot.vv` | 同上，`funct6=111101` | 16 个三值码双结果，零乘法器 | 已实现 |

V1 新增的"矩阵"语义全部靠**描述符 + CSR**，不占 opcode。这是与 openTPU 最关键的分野：它的 16 条私有 opcode 在 V1 里被替换成"RISC-V 的一小段代码 + 一次 doorbell 写"。

**风险点**：香山工具链若不认自定义指令，则需 `.insn` 手写编码或汇编器补丁。已有编码表，成本可控（见 05 文 T-SW 组用例）。

### 2.2 微架构可行性：每一层都有直接先例

| 层 | 做法 | 先例 |
|---|---|---|
| L1 向量 | 128-bit RVV + 3 条点积 | 本项目已上板级仿真链路 |
| L2 矩阵 | 8 列 × 64 深脉动 MXU，权重广播 | openTPU `docs/mxu_systolic.md`（D=128 × MCOLS=8，已上板） |
| 控制 | 描述符环 + 每周期一条"宏操作"的顺序发射 | openTPU 的 sequencer（每周期 1 条） |
| 主机接口 | AXI4-Lite CSR + AXI4 大数据通道 | openTPU `otpu_ctrl.sv` + `tb_board.sv` |

我们的 MXU 只有 openTPU 的一半深（D=64 vs 128）、同样列数，属于**参数缩小**而非新结构，风险显著低于从零发明。

### 2.3 数值可行性：位宽可以严格证明

整数域契约（借 openTPU 的"精确整数 + 每输出一次 epilogue"，`docs/isa.md:204-226`）：

```
acc = Σ_groups (m_g << sh_g) · c_g         全整数、无舍入
y   = (i2f(acc) · Sw) · (Sa · 2^-W)        每输出只做 3 次舍入乘
```

上界推导（D=64；**分组与 openTPU 一致：block = 64 个元素，group = D/4 = 16 个元素，每 block 4 个 group**）：

| 精度 | 单个 group 内积 `\|c\|` 上界（16 元素） | 缩放因子 `B = m<<sh` | 归约长度 K 上限 | `\|acc\|` 上界 | 48 bit 余量 |
|---|---|---|---|---|---|
| int8 | 16 × 128 × 127 = 260,096 < 2^18 | 2^16 | 4,096（256 组） | 2^42 | 32× |
| int4 | 16 × 128 × 8 = 16,384 = 2^14 | < 2^17 | 4,096 | < 2^39 | 256× |
| 三值 | 16 × 128 = 2,048 = 2^11 | < 2^11 | 4,096 | < 2^31 | 65,536× |

全部远小于 `2^47`，**48-bit 精确累加器足够，且不需要饱和逻辑**（只有错误检测）。

> 与寄存器级契约的衔接：`vdot` 的 INT8 输出是 20 bit 定长（实测 `ACC_W=20`，`|S| ≤ 131,072 < 2^17`）、INT4/三值是 12 bit（`|r| ≤ 512` 与 `≤ 1024`）。tile 级整数结果必须等于"若干个 `vdot` 结果按 `2^sh` 移位后累加"，这就是 G3 的可验证形式。

### 2.4 面积可行性

器件：Xilinx Kintex-7 **xc7k480t**（298,560 LUT / 2,980 DSP / 955 BRAM36），与 openTPU 同卡，便于横向对照。

| 模块 | LUT 预算 | DSP 预算 | BRAM36 | 依据 |
|---|---|---|---|---|
| MXU（8 列 × 64 深，512 MAC/cycle） | 30,000 | 160 | 0 | openTPU 1,024 MAC 用 267 DSP，按比例折半 |
| TMEM 64 KiB | 2,000 | 0 | 16 | 双口 RAM 复制 |
| ACT RAM 128 KiB | 1,500 | 0 | 32 | 64 行 × 32 块 × 64 B |
| DMA（2D strided，1024-bit） | 8,000 | 0 | 8 | 参照 openTPU `otpu_native_dram` 量级 |
| 前端 / 描述符队列 / 发射 | 5,000 | 0 | 2 | 顺序发射，无预测 |
| VPU + 量化 | 4,000 | 0 | 2 | 复用 `vdot` 思路 |
| CSR / 计数器 / 胶合 | 3,000 | 0 | 0 | — |
| **合计（预算）** | **≈ 53,500** | **≈ 160** | **≈ 60** | 占器件 18% LUT / 5% DSP |

对照：openTPU 整机 82,224 LUT / 267 DSP（`docs/status.md`）。我们的预算比它低 35%，与"MAC 数减半 + 少一套私有 ISA 译码"的直觉一致。

**风险**：预算不是实测。M2 必须用 Yosys 先出一次 generic 计数，M3 再用 Vivado 出 fmax，未达标就缩 `MCOLS` 或 `D`。

### 2.5 带宽可行性（这是 V1 的真瓶颈）

平台口径与 openTPU 一致（`docs/host.md:17`）：**每通道 64-bit DDR3-1066 = 8.53 GB/s，双通道 = 17.07 GB/s**，对应 128 B/beat @ 133.33 MHz。

我们 V1 取同一口径：**AXI4 1024-bit @ 133.33 MHz = 17.07 GB/s**。但需明确两种部署：

| 部署 | 可用带宽 | MXU 利用率上限（需 128 B/cycle） |
|---|---|---|
| 双通道 DDR3-1066（与 openTPU 同卡） | 17.07 GB/s | 100% |
| 单通道 | 8.53 GB/s | 50% |

因此规格里必须写成 **"AXI 峰值 17.07 GB/s；单通道部署时 MXU 利用率上限 50%"**，不能只报理想值。

带宽决定的两条曲线（V1 目标频率 133.33 MHz，512 MAC/cycle = 68.3 GMAC/s = 136.5 GOPS）：

| 场景 | 算术强度 | 瓶颈 | 结论 |
|---|---|---|---|
| Prefill GEMM（M=N=K=4096） | 2·M·N·K / (M·K+K·N+M·N) ≈ 2,730 op/byte | 算力 | 计算受限，理论上限 ≈ 1.0 s/GEMM |
| Decode GEMV（7B 模型，batch=1） | ≈ 2 op / 权重字节 | 带宽 | 见下表 |

Decode 带宽上限（17.07 GB/s，仅算权重）：

| 精度 | 7B 权重体积 | 时间/ token | 上限 tok/s |
|---|---|---|---|
| int8 | 7.0 GB | 0.41 s | 2.4 |
| int4 | 3.5 GB | 0.205 s | 4.9 |
| 三值 | 1.75 GB | 0.102 s | 9.8 |

**这张表就是三值/INT4 存在的理由**：decode 阶段算力大量闲置，位宽直接换成速度。

### 2.6 工具链可行性

| 环节 | 工具 | 现状 |
|---|---|---|
| RTL 建模 | SystemVerilog + Chisel（与香山一致） | 已有 `VDot.scala` / `VDotCore.sv` 生成链路 |
| 功能仿真 | Verilator | 已有 3,032 协同用例的流程 |
| 综合 | Yosys 0.52（`.tools/yosys`，已装）+ Vivado（无，需外部） | generic 计数可本地出；fmax 需 Vivado |
| 黄金模型 | Python（`tests/ref_vdot.py` 扩展） | 已有，扩展为 tile 级 |
| 主板 | 无 PCIe 卡 | **只能到板级仿真（tb）为止**，不能出实测 tok/s |

**这是本项目的最大硬约束**：V1 的验收在"RTL + 板级仿真 + 微基准"截止，不承诺上板实测。

## 3. 与 openTPU 的取舍

| 维度 | openTPU | RiscvTpu V1 | 理由 |
|---|---|---|---|
| 控制面 | 16 条私有 8×32-bit 宏指令 | RISC-V 代码 + 64 B 描述符 + CSR | 保留"是 RISC-V"的身份，可直接用 GCC/LLVM |
| 编译器 | 自研 Bend + 编译器 | 不做；用 intrinsics + 描述符生成器 | 需求内不需要图编译器 |
| 地址空间 | 私有 4 GiB 逻辑空间，双通道 64 B beat 交织 | 平坦物理地址，单通道 AXI | SoC 里不能自带交织（见 02 文 §6） |
| 数值契约 | 精确整数 + 每输出一次 fp32 epilogue | **相同**（直接借用） | 已被 10 个模型验证，且与我们"整数域可对拍"一致 |
| 4-bit 满速 | `PAIR`（`2*M <= MCOLS`） | V1 不做 tile 级 PAIR，只做"位宽减半→带宽减半" | ACT RAM 读带宽翻倍代价高，V2 再评估 |
| 三值 | 无格式，只能退化成 int4 | **原生 2-bit 码** | 我们已有的增量能力 |
| 观测性 | CSR 映射 `CYCLES/ICOUNT/端口计数` | **相同布局族**，增加 per-mode 退休计数 | 便于横向对照 |
| 许可证 | Apache-2.0 | 只借鉴思路，不复制代码 | 若复制需保留 LICENSE/NOTICE |

## 4. 风险与缓解

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | MXU 综合后 LUT/DSP 超预算 | 中 | 高 | 参数化 `MCOLS/D`；M2 先出 generic 计数，超标先降 `D` 到 32 |
| R2 | 133 MHz 下 MXU 时序不收敛 | 中 | 高 | 权重广播打拍、列内 DSP 级联、ACT RAM 前置寄存器；必要时降到 100 MHz 并把承诺改成相对值 |
| R3 | 无板卡，性能只能仿真 | 高 | 中 | 全部性能数字标注"仿真/上限"；用周期精确模型 + AXI 带宽模型 |
| R4 | 缓存一致性写错 | 中 | 高 | V1 只用 `cbo.clean/inval` + 显式 fence，不做硬件一致性；测试用"写后读回"用例强制覆盖 |
| R5 | 描述符格式过早固化 | 中 | 中 | 描述符预留 `w15` 与 8 个 flags 位；V1 冻结后只允许追加 |
| R6 | 与 `vdot` FU 重复造乘法器 | 低 | 低 | 明确分工：`vdot` 服务 GEMV/epilogue，MXU 服务 GEMM，不共享 EX1 |
| R7 | 三值在 tile 级无加速 | 高 | 低 | V1 的三值收益只来自**带宽**，明确写进规格，不宣称 MAC 数提升 |

## 5. 为什么不把 `vdot` 做成 openTPU 的私有宏指令

三个硬约束（与 `../openTPU-main/docs/vdot-integration/02_与vdot对接评估.md` §5 一致）：

1. **吞吐**：MXU 每列每周期归约 64~128 个 int8 乘积，`vdot` 一次 8 路；当 PE 会掉 8~16 倍。
2. **契约**：MXU 要 48-bit 精确累加，`vdot` 是 20/12 bit 定长；硬接会破坏其中一方的位精确性。
3. **身份**：`vdot` 最大的价值是"能被现有 RISC-V 工具链使用"。改成私有宏指令等于自断生态。

因此本项目的正确做法是**分层共存**：`vdot` 留在 VFEX0 服务向量路径，MXU 作为独立 tile 引擎，两者通过"整数域逐位可复算"这一条契约绑定。

## 6. 结论

**Go（有条件）。**

- **技术可行**：三层都有先例，MXU 是 openTPU 的参数缩小版，`vdot` 已实测落地。
- **数值可行**：三种精度的 48-bit 上界均有 ≥32× 余量，无需饱和逻辑。
- **面积可行（预算）**：≈53.5k LUT / 160 DSP，占 xc7k480t 的 18% / 5%。
- **带宽是主要矛盾**：decode 受 17.07 GB/s（单通道 8.53 GB/s）限制，int8/int4/三值分别约 2.4 / 4.9 / 9.8 tok/s 上限（单通道再折半）；这也正是位宽扩展的价值。
- **三项必须前置解决的条件**：
  1. M2 综合必须落在预算内，否则先降 `D`；
  2. V1 只承诺板级仿真，不承诺上板；
  3. 一致性方案只能走软件维护（`cbo` + fence），不引入硬件一致性。

若上述条件成立，进入 M0（规格冻结）。
