### 1.2 三条对策略起决定作用的推论

1. **"完成度逐级评价" ⇒ 阶段一是必得分，阶段三是加分项。**
   阶段一（环境部署 + hello 输出 + 操作日志 + 向量加法波形分析）成本最低、确定性最高，但一旦缺失会直接拉低整份作品档位。因此计划把阶段一压缩到 W1 前 3 天闭环，绝不允许被 RTL 工作挤占。
2. **"复用现有向量实现"是明确的架构约束，也是评分点。**
   不是新写一条独立流水线，而是把 vdot 挂在昆明湖 V2 既有的向量发射/写回框架上（新增 VFu 而非新增流水线）。设计文档必须显式回答"复用了什么、新增了什么、为什么不改主干"。
3. **阶段三的"加速比"必须有可复现的测量方法学。**
   基线不能只写"用几条指令替代"，而要给可运行汇编序列、周期计数方法与波形证据。否则性能结论不可信，这是最常见的失分点。

### 1.3 官方语义（伪代码）与歧义

赛题图中的官方伪代码：

```python
def vdot_vv(vs1, vs2, sew=8):
    # 根据 SEW 设定，从两个源向量寄存器中各取 8 个 int8 数据
    result = 0
    for i in range(8):
        result += sign_extend(vs1[i]) * sign_extend(vs2[i])
    vd[0] = result          # 结果写入目标向量寄存器 vd 的第一个元素
    vd[1..VLEN-1] = 0       # 其他通道清零
```

由此可确定：分组长度 K=8、输入为有符号 int8、点积后单点输出、其余通道清零。但存在 4 处必须由我们"显式裁决并写入规格"的歧义：

| # | 歧义 | 本方案裁决（口径 A） | 若官方另有口径的切换成本 |
|---|---|---|---|
| A1 | `vd[0]` 的元素位宽未定义（8 bit 装不下结果） | 结果按 **32 bit** 写入 vd[31:0]，vd[127:32] 全 0 | 参数 `OUT_W` 一处可改 |
| A2 | VLEN=128 却有 16 个 int8 通道，伪代码只用了 8 个 | 使用 vs1[63:0]/vs2[63:0]，高 64 bit 忽略 | 参数 `GROUP_K` 一处可改 |
| A3 | `vd[1..VLEN-1]=0` 的下标含义（元素 vs 位） | 按"位"解释：除 vd[31:0] 外全部清零 | 同上，属输出布局 |
| A4 | 编码未给出 | 采用 OP-V(0x57)/funct3=OPIVV/funct6=0b100000 的建议编码，且做成单点可配 | Decode 表一处常量 |

裁决依据与位宽推导见 [01 设计规格书 §2](file:///mnt/hdata/qxriscv/cieriscv/ipd/01_vdot指令与微架构设计规格书.md)。**D1–D2 必须发出语义确认（组委会/赛题答疑），但不等答复即可开工**——所有分歧点均已参数化，答复到达后只改参数与文档，不改架构。

## 2. 项目目标与成功标准

### 2.1 目标（MoSCoW）

| 级别 | 目标 | 验收口径 |
|---|---|---|
| **Must** | 阶段一全部交付 | 环境可复现部署 + `hello xiangshan, I am <team>, IP <addr>` 输出 + 完整操作日志 + 基于波形的 vadd 执行过程文档 + 录屏 |
| **Must** | 阶段二设计与实现 | 设计文档（语义/微架构/数据通路）+ Chisel RTL 集成进昆明湖 V2 + 正数/负数/边界值三类测试通过 |
| **Must** | 可提交的仓库与 PR | 公有仓库结构完整、可复现构建、`submit.sh` 加密提交、PR 标题符合官方格式 |
| **Should** | 阶段三验证与优化 | NEMU 扩展 vdot + NEMU/RTL 协同仿真一致 + 基线指令序列 + latency 加速比报告 |
| **Should** | 可量化收益 | 加速比数据可复现（脚本 + 波形 + 计数方法），并给出面积代价量级估算 |
| **Could** | 扩展增强 | LMUL>1 语义、`vd` 双半区并行点积变体、形式化断言、覆盖率报告 |
| **Won't（本期不做）** | 超范围工作 | 不改动香山主流水线结构、不做物理实现/流片、不做非官方语义的"性能优化版指令" |

### 2.2 项目成功标准（Definition of Success）

1. 三阶段交付物 100% 覆盖 [04 对照表](file:///mnt/hdata/qxriscv/cieriscv/ipd/04_评审对照与提交检查表.md) 的 Must 项，且每项都有"可点开的证据"（文件/截屏/波形/视频时间点）。
2. 所有 P0 测试用例通过，协同仿真 0 mismatch。
3. 加速比结论有 ≥3 次重复测量与中位数，且给出测量误差说明。
4. 第三方（指导老师/同学）按仓库 README 能在 1 小时内复现构建与跑通测试。

```
                 ┌─────────────────────────── W3 ───────────────────────────┐
                                              ▼
                        NEMU 建模 ──► difftest 协同仿真 ──► 基线序列 ──► 周期测量(波形+mcycle)
                                              │

                        加速比分析 ──► 文档定稿/回归 ──► 录屏+PPT ──► 仓库加密提交 + PR
```

**技术栈**：`xs-env`（香山开发环境）· Chisel/Scala · Verilator（emu 仿真）· NEMU（参考模型）· difftest · GTKWave/波形 · RISC-V 汇编与裸机测试程序 · Python（golden model / 数据统计）。

**核心设计取向**：单 uop、状态无关、全流水、只挂钩既有 VFu 框架。理由：4 周工期下，"可集成、可验证"优先于"极致 PPA"；且状态无关设计天然规避 `vstart` 重放复杂度（见 01 §2.5）。

## 5. IPD 流程裁剪与门径

IPD 标准六阶段（概念→计划→开发→验证→发布→生命周期）在 4 周赛题场景下做如下裁剪，保留**决策评审点（DCP）**与**技术评审（TR）**，去掉与量产相关的市场/制造环节。

| IPD 阶段 | 本项目的映射 | 决策/技术评审 | 出口准则（Exit Criteria） |
|---|---|---|---|
| 概念 Concept | W1 D1–D3：赛题解读、语义裁决、可行性判断 | **CDCP**（D3） | 语义歧义清单已裁决且有回退方案；环境跑通；阶段一可交付 |
| 计划 Plan | W1 D3–D5：规格书、测试方案、WBS | **PDCP**（D5）+ TR1（需求评审） | 规格 v1.0 冻结；用例矩阵覆盖三类必测；WBS 到人日 |
| 开发 Develop | W2 D6–D10：RTL 实现与集成 | TR2（设计评审，D7）、**TR3**（D10） | 编译通过、集成不破坏既有回归、三类功能测试全绿 |
| 验证 Verify | W3 D11–D15：NEMU、协同仿真、性能 | TR4（D15） | difftest 0 mismatch；基线正确；周期数据可复现 |
| 发布 Release | W4 D16–D20：报告、录屏、提交 | **TR6 + ADCP**（D20） | 交付物对照表 100%；加密提交完成；PR 已创建 |
| 生命周期 | 赛后（可选）：社区回馈、issue 答复 | — | — |

**跨职能并行**（IPD 的核心思想，此处落到 3 人）：RTL 设计、验证环境、文档/提交三条线从 W1 起就同时启动，而不是"先写完代码再补测试"。文档工作前置到 D3（写规格）而非 D19（补报告）。
